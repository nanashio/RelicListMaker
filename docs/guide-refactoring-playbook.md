# リファクタリング作業プレイブック

このドキュメントは、既存コードを段階的にモジュール化しながら安全にリファクタリングする際の共通手順をまとめたものです。個別プロジェクトの事情に合わせて読み替えてください。

## 0. 分析と合意形成フロー
1. **コード分析**: 対象コードを読み、重要な箇所や構造をマークダウンで要約する。
2. **問題点の指摘**: 長すぎる関数、複雑な条件分岐、責務の混在などを簡潔に列挙する。
3. **優先度提案**: 重大な問題から順に解決策を提案し、必ず合意を得てから次に進める。
4. **小ステップ実行**: 各問題を小さなステップに分解し、1つずつ提案・実行。ステップごとに結果を確認しながら進める。
5. **影響確認**: ステップ実施後は副作用がないか確認し、必要に応じて追加提案を行う。
6. **まとめと次フェーズ**: すべて完了したら改善点を要約し、次に取り組むべき課題を提案する。

このフローはリファクタリングを依頼されるたびに繰り返す。

## 1. 作業前の準備
- 変更計画を記録するドキュメント（例: `docs/<project>-refactor-plan.md`）を用意し、ステップごとに進捗を追記する。
- メイン開発環境と成果物を取り込む環境が分かれている場合は、同期スクリプト（例: `docs/build_windows.ps1`）で差分を取り込んだ上でビルド確認する。
- 動作確認に必要なサーバ／ブラウザ／テストツールを起動できるよう整えておく。

## 2. モジュール切り出しの基本ルール
1. **対象機能を特定**: 単一責務を持つ関数や処理ブロックを洗い出す。
2. **外部モジュール化**: 新しい IIFE や ES モジュールで公開し、グローバル (`window.myFeatureFactory` など) 経由で利用できるようにする。
3. **フォールバック保持**: 既存バンドルが単体でも動くよう、モジュール未ロード時は従来実装を使うコードを残す。
4. **依存方向の整理**: 下層（状態・データ）→上層（アプリ・UI）の一方向依存を徹底し、循環参照を避ける。
5. **段階的差し替え**: 切り出したら元の実装を削除し、新モジュール経由で呼び出すコードに置き換える。

モジュールの配置例:
- `state/` … ストア・状態管理
- `storage/` … 読み込み／保存ユーティリティ
- `dataset/` … データセットやフィルタ切り替えなどの業務ロジック
- `app/` … 初期化コントローラや起動シーケンス
- `utils/` … DOM 操作や共通関数

## 3. ステップの進め方（例）
1. UI コンポーネントのヘルパー化（DOM 構築／イベント整理）。
2. 状態ストアの外部モジュール化と購読・通知の整備。
3. 読み込み・保存処理の外部化（ストレージユーティリティ）。
4. データ切り替え／業務ロジックの外部化。
5. アプリ初期化シーケンスの外部化（エントリポイント分離）。
6. 必要に応じて ES モジュール化やテスト追加を検討。

プロジェクトにより順番は変わっても構わないが、依存度の低い層から高い層へ移行すると安全。

## 4. 実装時の注意点
- フォールバックの有無を常に意識し、既存環境でも動作が壊れないことを確認する。
- 可能な限り `window.myFeatureFactory` のようにグローバル名を一元管理すると把握しやすい。
- `state -> data -> storage -> app -> ui` など、依存チェーンを意識して配置する。
- ストアの購読 (`subscribe`) は、必要な依存関数が揃った後に設定する。
- 同期スクリプト（`build_windows.ps1` など）を使う場合は、コピー対象や除外ディレクトリを調整して差分を確認しやすくしておく。

## 5. 動作確認のテンプレート
1. 同期スクリプトを実行し、差分が正しくコピーされるか確認。
2. ブラウザやサーバ上で対象機能が想定通り動作するかをチェック。
3. 変更計画ドキュメントに進捗・注意点を追記。
4. `npm run test:all` を実行し、Python・Node・Playwright の一括テストで回帰が無いことを確認。
5. `git status`・`git diff` で変更内容を確認し、問題が無ければコミット。

## 6. よく使うコマンド例
```powershell
# WSL -> Windows へ同期しビルド (環境に応じてパス変更)
PS> .\docsuild_windows.ps1 -WslPath '/home/user/project'

# 差分確認
$ git status -sb
$ git diff [--staged]

# サーバ起動 (例)
$ python viewer_server.py --results ./results
```

## 7. ペンディング課題の記録
- コピー結果の表示改善やテスト追加など、未着手の改善点は都度この節に追記する。
- 次回リファクタリング時に参照し、優先順位を決める際の材料とする。

このプレイブックをベースに、プロジェクト固有のルールや検証手順を追記して自分たち専用のガイドに育ててください。
