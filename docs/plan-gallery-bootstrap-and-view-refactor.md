# ギャラリーブートストラップとビュー初期化の整理計画

## 背景と目的
- 直近の改善でモジュール manifest 化は進んだものの、ブートストラップとビュー初期化周りに肥大化・煩雑さが残り、可読性と変更容易性を阻害しています。【F:templates/gallery/index.js†L28-L107】【F:templates/gallery/render/galleryView.js†L65-L226】
- 本計画では、データ適用と依存解決の責務分離、非同期ロードの明確化、ビュー構築フローの段階化を行い、将来の機能追加（フィルター・タグ処理など）でも拡張しやすい構造を目指します。
- **目的を「コード量削減 × 可読性向上」に揃え、重複ロジックや過剰なフォールバックを間引いて、変更容易性の高い最小構成へ寄せる。**

## 対象とスコープ
- 対象: `templates/gallery/index.js` のブートストラップ処理と依存ロード、`templates/gallery/render/galleryView.js` のビュー初期化・再構築処理。
- スコープ外: Python パイプライン、TomSelect アダプタ既存 API の変更。既存 manifest (`moduleEntries.js`) のベース構造は維持しつつメタデータ拡張のみ行う。

## 現状課題の整理
1. **ブートストラップデータの検証不足と大量の dataset 書き戻し**
   - `applyBootstrapData` が 20 以上の dataset 更新を直列で実施し、必須/任意やフォールバックの区別がコードから読み取りにくい。【F:templates/gallery/index.js†L56-L107】
2. **依存ロードの直列化と意図の不透明さ**
   - manifest で依存一覧を得ているが、`loadDependencies` が逐次 `await import` を行い、並列可否や順序保証の意図が共有されていない。【F:templates/gallery/index.js†L22-L39】
3. **ビュー初期化とフォールバック解決の肥大化**
   - `galleryView` でグローバル/ストア/フォールバック判定が連続し、タグトークン解析やデバッグ設定の解決経路が複雑。【F:templates/gallery/render/galleryView.js†L65-L226】
   - 描画・状態キャッシュ・フィルター適用が単一関数に詰め込まれ、再描画手順を追うのにコストが高い。

## 解決方針とタスク
### 1) ブートストラップデータのバリデーションと適用の分離
- `validateBootstrapConfig(schema, rawData)` を `templates/gallery/js/modules/` に新設し、必須項目（coreScript, resultsCsv など）と任意項目のデフォルトをスキーマで宣言する。
- `applyBootstrapData` を「検証済み設定を dataset へマッピングする」責務に限定し、マッピング表（キー/フォールバック/変換関数）を定義して 1 行ループで適用できるようにする。
- バリデーションエラーや欠落は `console.warn` で明示し、生成された `gallery_data.json` が壊れている場合の早期検知を狙う。
- **デフォルトを共通マッピング表に集約し、重複書き戻しを除去することで dataset 適用コード行数を 30% 以上削減する。**

### 2) 依存ロードのメタデータ化と並列化
- `moduleEntries.js` の manifest に `load: 'sequential' | 'parallel'` や `group` を追加し、順序必須モジュールのみ逐次ロード、その他は `Promise.all` で並列読み込みするロジックに分岐する。
- 依存グループごとにロード時間と失敗ログをまとめるトレーサを実装し、初期化時間の計測とボトルネック特定を容易にする。
- 並列ロードで競合しないことを Node テストで確認する（例: 互換レイヤーは sequential, UI ユーティリティは parallel）。
- **不要になったフォールバック import や未使用モジュールを manifest から排除し、読み込み対象をスリム化する。**

### 3) ビュー初期化の責務分割とフォールバック解決の明文化
- `resolveGalleryDependencies(config)`（仮）を導入し、デバッグ設定・タグトークンリゾルバ・共有リゾルバの解決をまとめた小さな工場に分離する。`createGalleryView` には解決済みハンドラを渡すだけにする。
- `buildGallery`（描画＋キャッシュ＋フィルター）を段階関数に分割：`prepareRenderState`（データ整形・キャッシュ）→`renderGalleryView`（DOM 生成）→`wireGalleryFilters`（イベント購読）のように責務を切る。
- フォールバック順序と優先度をテーブル化し、デバッグログにも同じ順序を出力できるようユーティリティを整備する。
- **段階関数ごとに純粋関数化・共有化できる処理を抽出し、IIFE 互換レイヤーとの重複ロジックを統合して総行数を圧縮する。**

### 4) テストと運用の更新
- Node テストにブートストラップスキーマ検証のケース（必須欠落・型不整合・デフォルト適用）を追加。
- 依存ロードの並列化に伴う順序保証を manifest ベースで検証するテストを拡充。
- ビュー初期化の分割後は、純粋関数化した整形・フォールバック解決を個別にテストし、IIFE 互換ラッパー経由の動作確認も `node --test` で継続する。

## スケジュールと成果物
- **Sprint A (ブートストラップ)**: スキーマ定義＋マッピングリファクタ（1 日）→ `templates/gallery/index.js` 差し替えとテスト追加。
- **Sprint B (依存ロード)**: manifest 拡張と並列ロード実装（1 日）→ ロード時間/失敗ログの可視化。
- **Sprint C (ビュー初期化分割)**: 依存解決ファクトリと段階関数導入（2 日）→ `galleryView` の責務分離とテスト更新。
- **成果物**: 更新後の設計図（本書追記）、テストログ（pytest / node --test）、ロードトレーサのメトリクス。

## リスクと緩和策
- 並列ロードで暗黙依存が露呈するリスク → manifest で順序必須を明示し、テストで検出できるようにする。
- スキーマ厳格化で既存 `gallery_data.json` が弾かれるリスク → 非互換項目には暫定互換ハンドラを用意し、警告ログで移行を案内する。
- ビュー分割に伴う IIFE 互換漏れ → 互換レイヤーを残しつつ、新ファクトリに渡す依存を IIFE でも解決できるブリッジを用意する。
