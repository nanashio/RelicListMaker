# GUI アプリ リファクタリング計画（旧 `gui_app.py`）

## 0. コード分析
- `gui/app.py`（旧 `gui_app.py`）は 700 行超の単一ファイルで、Tkinter UI 構築・ドラッグ＆ドロップ対応・バックグラウンド実行・ログ出力・HTTP サーバー起動・CSV マージなどを一括で扱っている。
- `_build_layout` がウィジェット生成、イベントのバインド、状態初期化をまとめて実行しており、130 行規模の複雑なブロックになっている。
- `on_run_pipeline` / `_run_pipeline_thread` がフォーム検証、進捗コールバック、例外処理、CSV マージ、ビューワ起動までを抱え込み、UI フリーズ回避のためのスレッド制御と状態更新ロジックが混在している。
- ドラッグ＆ドロップ (`DropTarget` / `_configure_drag_and_drop`) やログリダイレクト (`QueueHandler`, `_install_logging_handler`) は GUI と直接結合しており、テストや差し替えが困難な構造となっている。

## 1. 問題点
1. **責務過多のクラス構造**: `RelicListApp` が UI コンポーネント、設定保持、パイプライン起動、結果ビューワ操作をすべて内包し、単一責任原則から逸脱している。
2. **イベントハンドラの肥大化**: `_build_layout`, `on_run_pipeline`, `on_merge_results` などのメソッドが 100 行規模で、状態遷移と副作用が読み取りづらい。
3. **バックグラウンド処理と UI 更新の混在**: スレッド起動 (`threading.Thread`) と UI 更新 (`tk.StringVar`, `messagebox`) が同一メソッドに書かれ、エラーハンドリングの分岐が重複している。
4. **依存モジュールの直接参照**: `pipeline.run_pipeline`, `viewer_server.create_server`, `merge_results.merge_results` を直接呼び出しており、モックによるテストや CLI ラッパーからの再利用が困難。
5. **設定値・パス処理の散在**: 入力/出力ディレクトリ検証、CSV パス生成、レビュー CSV の統合などが UI メソッド各所に分散し、再利用や単体テストができない。

## 2. 優先度提案
- **最優先**: UI レイアウト生成とイベントハンドラからビジネスロジックを分離し、テスタブルなサービス層を導入する（問題1〜3）。
- **次優先**: パイプライン実行／マージ処理のオーケストレーションをヘルパーモジュールへ切り出し、依存注入で差し替え可能にする（問題4,5）。
- **中期的対応**: ログ/通知チャネルを抽象化し、CLI/GUI 両対応の構造へ整理する。

## 3. 実施ステップ
1. **レイアウト生成の分割**: `_build_layout` を UI セクションごとのファクトリ関数（例: `_build_input_section`, `_build_controls_section`, `_build_progress_section`）に分解し、ウィジェット参照は `NamedTuple` や dataclass で集約する。
2. **状態管理オブジェクトの導入**: 入力設定や処理状態を表す `GuiState` dataclass を新設し、Tkinter 変数と分離した状態モデルを `RelicListApp` に注入する。UI ↔ 状態同期は専用メソッドに委譲する。
3. **パイプライン実行サービスの抽出**: `PipelineExecutor`（仮称）を `gui/services.py` に追加し、`run_pipeline` とマージ処理、ビューワ起動のフローをまとめる。GUI 側はコールバックと結果を受け取るだけに留める。
4. **バックグラウンド実行の共通化**: スレッド起動・例外捕捉・UI スケジューラへのポスト処理を `BackgroundTaskRunner` などのヘルパーへ切り出し、`on_run_pipeline` からはコマンド生成とハンドラ登録のみ行うよう変更する。
5. **ドラッグ＆ドロップ・ログの分離**: DnD 設定やログキューを `gui/adapters.py` などの専用モジュールに移し、Tkinter へのバインドを小さなアダプタクラス経由で行う。GUI テスト時にはスタブを注入できるようにする。
6. **段階的テスト整備**: 分離したサービス層に対して `pytest tests/test_gui_services.py`（新設）でユニットテストを追加し、既存 GUI は `tkinter` モックで最小限の回帰確認を行う。

## 4. テスト戦略
- UI ロジック分離後に `pytest -k "gui"`（新規パターン）を追加してサービス層を検証する。
- フルパイプライン確認として、従来どおり `python -m gui --results ./results` を手動確認リストに残し、ドラッグ＆ドロップやログ表示が維持されているか確認する。
- バックグラウンド実行ヘルパーは `tests/fixtures/threading.py`（必要なら新設）で疑似スレッドを使った単体テストを行う。

## 6. ペンディング課題
- Playwright 等で GUI を自動化できないため、Tkinter ウィジェットの結合テスト手法（pytest-tkinter など）を調査する。
- Windows 固有のコンソール接続 (`_windows_cli_output`) をサービス層へ切り出す際の互換性確認が必要。
